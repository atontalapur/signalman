## Problem Statement

Plan A (`docs/superpowers/plans/2026-09-10-sigma-frontend.md`) turns Sigma
rule YAML into a bound, evaluable AST plus the event value model, and proves
the semantics against pySigma. The plan is fully written. This session settled
how to execute it, which of its parts are stale, and what the second-opinion
review found before any code exists. The user's goal is learning: Go,
parsers, detection engineering.

## What Makes This Cool

- The differential fuzzer is the showable artifact. pySigma-backend-sqlite
  has real semantic gaps; a minimal repro filed upstream is a portfolio line.
- The bound AST hash computed for `RuleSetV` doubles as a fingerprint. Run
  over the SigmaHQ corpus it finds rules with identical or subsumed trees.
- `ast.String` plus `walkNode` are sixty lines from a verdict-colored tree
  printer. Plan B's `signalman explain` is the home for it.

## Constraints

From CLAUDE.md and the roadmap, non-negotiable:

- Verdict is a pure function of `(Event, RuleSetV, TaxonomyV)`.
- Aggregation rejected at load with rule ID, line, and the exact phrase.
- Case-insensitive string matching; `|re` case-sensitive unless `|re|i`.
- Purpose-built wildcard matcher, never regex translation.
- `internal/sigma/match` does not import `internal/sigma/ast`.
- One Jira story per branch, `feat/SIG-<n>-<slug>`, `/ship` opens the PR.
- Tests first for every task.

## Premises (agreed)

1. Hand-write the frontend; do not import `sigma-go` or similar. Owning the
   AST, determinism, and null-vs-empty semantics is the project.
2. pySigma via the SQLite backend is an independent enough oracle. Gaps go in
   `test/fuzz/KNOWN_DIVERGENCES.md`, one row per suppression.
3. The data contract (`Event`, `Value`, `Verdict`) is Task 1 of Plan A.
4. One branch and PR per story (S-10 to S-18), not one for the plan. The
   plan's line 23 and "Plan A exit" section are stale and must be corrected.

## Cross-Model Perspective

A fresh Claude subagent (same model family; weigh accordingly) read the plan
cold. It confirmed premises 1, 2, and 4 and did not challenge 3. Its concrete
findings, ordered by whether they break the fuzzer:

Task 14 (fuzzer), all blocking as written:
- `EvalOnce` gates on the logsource match but fuzz events carry no
  `channel` or `event_id`; the seed pair itself disagrees.
- SQLite table columns come only from the event's keys, so a rule field
  absent from the event is "no such column", not null.
- Backend emits `field = 'value'`, case-sensitive in SQLite. Columns need
  `TEXT COLLATE NOCASE` and the generator must stay ASCII.
- Events are `map[string]string`; numbers become TEXT and `EventID = 4688`
  compares false. Generate and insert typed values.
- No `REGEXP` function; register one. Keyword lists and unbound values raise
  `NotImplementedError`; both need `known()` rows.
- Raw YAML byte mutation yields mostly double-rejections. Seed a structured
  generator (field, modifier chain, value, event) from the fuzz bytes.
- Temp file per execution; add `LoadRuleBytes`.

Semantics, would be caught by a working fuzzer:
- Task 7 `WinDashVariants` expands only a leading dash; pySigma expands
  every `-` or `/` at a word boundary (cartesian product).
- Task 6 `escapeWildcards` checks the last two bytes; count trailing
  backslashes, odd means escape.
- Task 9 silently discards transforms before `re` and `cidr`; accepts `|i`
  without `re`; transforms encode a literal `*` as bytes.
- Task 8 `Compare` is int64 only; pySigma accepts floats.
- Task 11 `Resolve` requires the entry to be at least as specific as the
  rule, which is backwards for a taxonomy.
- Task 10 keywords are `Contains` over all fields; spec says whole-value
  match with wildcards. Decide and document.

Corpus realities the plan does not mention:
- `condition` as a YAML list; duplicate rule IDs; `|exists`, `|cased`;
  `action: global` collections. `RuleSetV` hashes `Pred.Desc`, which does
  not escape quotes and can collide.

Existing code worth reading, not importing: `bradleyjkemp/sigma-go` (rule
model, evaluator; translates wildcards to regex), pySigma `modifiers.py` and
`types.py` (de facto spec for `windash`, `base64offset`), Zircolite (the
SQLite-oracle approach; check its table build and `COLLATE`).

## Approaches Considered

### Approach A: Plan as written, sequential
Tasks 1 to 14 in order, one PR per story. Corpus report and fuzzer arrive
last, after nine merged PRs. Rejected during the session: feedback too late.

### Approach B: Corpus-first reorder (chosen)
Same tasks and PRs. Order: 1, 5, 6, 9 (minimal), 2, 3, 4, 10, 11, 12, then
13 (corpus report), then 14 (fuzzer, rewritten per the findings above), then
7, 8 and the rest of 9, driven by corpus counts and fuzz failures. Task 11
stays before 12 because 12, 13, and 14 all consume its types and loader; a
stub would be most of Task 11 under another name and would violate the
no-taxonomy-is-a-load-failure constraint.

### Approach C: Oracle-first minimal
Build the pySigma bridge first against a stub engine. Rejected during the
session: slow start, nothing showable, fights the backlog order.

## Recommended Approach

B. The two feedback loops run before the encoding and comparison modifiers
exist, so those are built against evidence. Story mapping is unchanged;
S-17 and S-18 land mid-sprint instead of at the end.

Task to story order under B. Nine PRs, one per story:

| Order | Tasks | Story | Branch |
|---|---|---|---|
| 1 | 1 event model | S-10 | `feat/SIG-13-event-value-model` |
| 2 | 5, 6, 9 minimal (see below) | S-12 | `feat/SIG-15-wildcard-string-modifiers` |
| 3 | 2, 3, 4 lexer, parser, expand | S-11 | `feat/SIG-14-condition-parser` |
| 4 | 10 detection compile | S-14 | `feat/SIG-17-detection-compile` |
| 5 | 11 taxonomy | S-15 | `feat/SIG-18-taxonomy` |
| 6 | 12 rule loader | S-16 | `feat/SIG-19-rule-loader` |
| 7 | 13 corpus report | S-17 | `feat/SIG-20-corpus-acceptance` |
| 8 | 14 fuzzer, rewritten | S-18 | `feat/SIG-21-pysigma-fuzzer` |
| 9 | 7, 8, rest of 9, fuzz allowlist growth | S-13 | `feat/SIG-16-encoding-modifiers` |

Task 9 (`match.Build`) is needed by Task 10. Step 2 ships `Build` handling
`contains`, `startswith`, `endswith`, `re`, `i`, `all`, and null; every
other modifier returns `ErrUnsupportedModifier` naming it, and Task 12
classifies it with `errors.Is`, not by matching error text. Step 9 adds the
encoding, comparison, cidr, and fieldref cases to the same function. The
corpus report at step 7 therefore counts those as `modifier` rejections,
which is the number that decides what step 9 builds.

The fuzzer at step 8 also predates step 9. Its structured generator draws
modifiers from an allowlist that starts as the step 2 set and grows with
step 9, so the fuzzer is never red for a modifier that is not built yet.
`LoadRuleBytes` (the fuzzer needs it) lands in S-16 with `LoadRule`.

Pins for reproducibility: the SigmaHQ corpus commit SHA is recorded in
`docs/corpus-acceptance.md` with each run; pySigma and the SQLite backend
are pinned to exact versions in `test/fuzz/requirements.txt`.

## Open Questions

- Keyword semantics: decided. Task 10 ships keywords as `Contains` over
  every field value, which is what most Sigma backends do for unbound
  values. This deviates from the Sigma spec's whole-value-with-wildcards
  reading and is recorded as a deliberate deviation in
  `KNOWN_DIVERGENCES.md`. The SQLite oracle raises `NotImplementedError`
  for keywords, so it cannot check either reading. The corpus report
  revisits if keyword rules are common.
- Whether `|exists` and `|cased` are in scope for Plan A or rejected with a
  `modifier` code and closed in Plan H. Decide from the corpus counts.
- `RuleSetV` input: hash a canonical serialization of the tree, not
  `Pred.Desc`. Shape to be fixed in the eng review.

## Success Criteria

Plan A gate from the roadmap: every rule in the SigmaHQ corpus loads or is
rejected with a code; counts and commentary in `docs/corpus-acceptance.md`;
the differential fuzzer runs 1e6 executions clean with every suppression
documented. Nine story PRs merged via `/ship`, `make check` green on each.
