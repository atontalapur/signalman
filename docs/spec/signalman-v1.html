00

Goals and non-goals

Signalman ingests normalized security events, evaluates Sigma rules against each one, and writes alerts. That much is a weekend project. The specification exists because of the second half: the evaluation core is written twice, and the second version replaces the first while traffic is flowing, under a written equivalence argument.

The build therefore produces two things. One is a working system. The other is a set of documents that record how the replacement was proven safe, which is the part that is hard to fake and hard to acquire outside of a job.

Goals

  • Parse and evaluate the Sigma specification correctly, including the condition grammar and the value modifiers, not a convenient subset.
  • Sustain 50k events/sec against a 1,500 rule corpus on a single 8-core node, with p99 end-to-end latency under 250ms.
  • Make degradation legible: when the pipeline falls behind, it is knowable whether detections were delayed or lost.
  • Detect the absence of expected work, not just the presence of errors.
  • Give rule authors a feedback loop that reports false-positive load before a rule merges.
  • Replace the evaluator with zero verdict divergence, on a staged rollout, with a rehearsed rollback.

Non-goals

  • Sigma correlations and aggregations. | count() > 5 by User requires stateful windowing and a different design. Rules using it are rejected at load time with a clear error rather than silently mis-evaluated. This is the single largest scope cut and it is deliberate.
  • Enrichment. No asset lookups, no threat intel joins, no geo. The normalizer maps fields and stops.
  • Case management. Alerts land in ClickHouse. Triage workflow is out of scope.
  • Multi-tenancy. One rule set, one taxonomy, one tenant.
Scope discipline

Every item on the non-goals list is a thing that will look tempting in week 6. Adding any of them costs the cutover, which is the only part of this project that a hiring panel cannot get from a hundred other candidates. Cut features before cutting phase 08.

01

Data contract

Equivalence between two engines is only checkable if there is a precise definition of what each engine emits. That definition comes first, before either engine exists, and it does not change after phase 04 ships.

internal/event/event.go
// Event is the unit of work. Seq is assigned once, at ingest, and is
// monotonic within a partition. Everything downstream is keyed on it.
type Event struct {
	Seq       uint64            // ingest-assigned, per-partition monotonic
	Partition int32
	Source    string            // "sysmon" | "auditd" | "cloudtrail"
	EventTime time.Time         // from the record, never wall clock
	IngestAt  time.Time
	Fields    map[string]Value  // taxonomy-mapped, normalized
	Raw       []byte            // retained for the alert record
}

// Value is a closed sum type. Sigma comparison semantics differ per
// kind, so the kind is carried explicitly rather than inferred.
type Value struct {
	Kind ValueKind // KindString, KindInt, KindBool, KindNull, KindList
	S    string
	I    int64
	B    bool
	L    []Value
}

// Verdict is the equivalence unit. One per (event, enabled rule).
type Verdict struct {
	Seq       uint64
	Partition int32
	RuleID    string // the Sigma `id:` UUID, not the filename
	Matched   bool
	Engine    string // "v1" | "v2"
	RuleSetV  string // content hash of the compiled rule set
	TaxonomyV string // content hash of the field mapping
}
Invariant 1 / total coverage

Every event admitted at ingest produces exactly one verdict per enabled rule, or exactly one entry in the drop ledger with a reason code. There is no third outcome. An event that vanishes without appearing in one of those two places is a P1 bug, and the pipeline has a continuous audit job that checks the arithmetic.

Invariant 2 / determinism

A verdict is a pure function of (Event, RuleSetV, TaxonomyV). No wall clock, no random source, no dependence on Go map iteration order, no dependence on the order rules were loaded. This is what makes replay a valid equivalence test, so it gets its own property test: evaluate the same corpus with the rule set shuffled ten times and assert the verdict stream hash is identical.

Invariant 3 / ordering

Alerts for a given partition are emitted in Seq order. Kafka partitioning is by host_id hash, so per-host ordering holds, and cross-host ordering is explicitly not guaranteed. Say this out loud in the doc, because a consumer will otherwise assume global ordering and be wrong.

Verdict stream hash

The single most useful piece of tooling in the whole project is three lines long. Fold every verdict into a rolling hash, per partition, in Seq order:

internal/verdict/digest.go
h = fnv1a64(h, seq, ruleID, matched)

Two engines that produce the same digest over the same corpus are equivalent on that corpus, and the check is a string comparison rather than a diff of forty million rows. The row-level differ still exists for finding out why a digest differs, but the digest is what goes in the cutover gate.

02

Sigma frontend

The frontend turns rule YAML into an AST. It is shared by both evaluators and by the ClickHouse backend, so a semantic bug here is a bug everywhere, and it gets the heaviest testing in the project.

Condition grammar

Write a real lexer and a precedence-climbing parser. The condition field looks simple enough to handle with string splitting, which is exactly the trap: selection and not (filter1 or filter2) and 1 of selection_* and not all of filter_* both appear in the SigmaHQ corpus and neither survives a naive split.

Condition grammar, EBNF
condition   := or_expr
or_expr     := and_expr ( "or" and_expr )*
and_expr    := not_expr ( "and" not_expr )*
not_expr    := [ "not" ] primary
primary     := "(" or_expr ")" | quantifier | IDENT
quantifier  := count "of" ( pattern | "them" )
count       := "1" | "any" | "all"
pattern     := IDENT [ "*" ]        # prefix glob over selection names

# precedence: not > and > or        (left associative)

Resolve quantifiers at parse time, not eval time. 1 of selection_* expands into an OR node over the matching selection identifiers, and all of them expands into an AND node over every selection defined in the rule. Doing the expansion in the parser means the evaluator only ever sees AND, OR, NOT, and leaf predicates, which keeps both engines small.

Reject loudly

If the condition contains a pipe, the rule uses aggregation and this engine cannot evaluate it. Fail the load with the rule ID, the line number, and the phrase "aggregation is not supported". A rule that is silently skipped is a missed detection with no signal attached to it, which is the worst failure this system can have.

Detection block semantics

The implicit boolean structure is where most homegrown implementations quietly diverge from the specification.

Implicit combination rules
ShapeMeaning
map of field: valueAND across the fields
field: [a, b, c]OR across the values
field|all: [a, b]AND across the values
list of mapsOR across the maps, AND within each
field: nullmatches when the field is absent or present and null
field: ''matches only a present, empty string. Not the same as null

Modifiers

Implement the full set, and implement wildcard matching as its own matcher rather than by translating to regex. The naive translation of * to .* breaks on values that contain regex metacharacters, and Windows command lines are full of them.

Value modifiers and their sharp edges
ModifierNote
contains, startswith, endswithCase insensitive by default, like all Sigma string comparison

Taxonomy mapping

Sigma logsources are abstract. process_creation on Windows means Sysmon Event ID 1, and the rule's Image field means Sysmon's Image but auditd's exe. That mapping is configuration, versioned, and hashed into TaxonomyV:

config/taxonomy/sysmon.yml
logsource:
  product: windows
  category: process_creation
match:
  channel: Microsoft-Windows-Sysmon/Operational
  event_id: 1
fields:
  Image:            Image
  CommandLine:      CommandLine
  ParentImage:      ParentImage
  User:             User
  OriginalFileName: OriginalFileName
  Hashes:           Hashes

A rule whose logsource has no taxonomy entry does not silently match nothing. It fails to load, with the same loud error as an unsupported condition.

Second backend

Once the AST exists, add a compiler that emits ClickHouse SQL for retro-hunting over the historical alert store. One specification, two execution targets, is the exercise that shows whether the AST is a real abstraction or just a shape the evaluator happens to like. Expect the leaks to show up in regex dialect (RE2 in both, fortunately), case-insensitive comparison, and null handling, and write those down as they appear.

03

Reference evaluator

v1 walks the AST once per rule per event. No index, no prefilter, no caching. It is intentionally the slowest correct thing that can be written.

internal/engine/v1/eval.go
func (e *Engine) Evaluate(ev *event.Event) []event.Verdict {
	out := make([]event.Verdict, 0, len(e.rules))
	for _, r := range e.rules {
		if !r.LogSource.Matches(ev) {
			out = append(out, verdict(ev, r, false))
			continue
		}
		out = append(out, verdict(ev, r, walk(r.Cond, ev)))
	}
	return out
}

func walk(n ast.Node, ev *event.Event) bool {
	switch n := n.(type) {
	case *ast.And: // short circuit is fine; it cannot change the result
		for _, c := range n.Children { if !walk(c, ev) { return false } }
		return true
	case *ast.Or:
		for _, c := range n.Children { if walk(c, ev) { return true } }
		return false
	case *ast.Not:
		return !walk(n.Child, ev)
	case *ast.Pred:
		return n.Match(ev)
	}
	panic("unreachable node type")
}

Two rules govern v1 for the life of the project. It is optimized for being obviously correct when read, and it is never deleted. After the cutover it stops serving traffic and becomes the oracle that the differential tests compare against, which means the codebase permanently contains a second, independent implementation of the semantics.

Invariant 4 / no rule skipping

Note that v1 emits a false verdict for a logsource mismatch rather than emitting nothing. Absent verdicts and negative verdicts are different states, and collapsing them makes invariant 1 uncheckable. v2 must preserve this, which is a real constraint on the prefilter design in phase 07.

Backpressure

Every stage boundary is a bounded channel. There is no unbounded buffer anywhere in the process, and the code review checklist has a line item for it. The worker pool per stage is sized at GOMAXPROCS and configured, not computed at startup, so that load tests can pin it.

Decision / lag over loss

When the matcher cannot keep up, the bounded channel fills, the consumer stops polling, and Kafka consumer lag grows. Signalman does not shed load. Lag is visible, bounded by retention, and recoverable by replay. Silent loss is none of those. The one place events are discarded is a parse failure, and every discard is written to the drop ledger with a reason code and the raw bytes.

Offsets are committed manually and only after the verdicts for that batch are durable, which makes delivery at-least-once. Duplicates are absorbed at the sink: the ClickHouse alert table is a ReplacingMergeTree ordered by (partition, seq, rule_id), so a redelivered batch collapses on merge. Write down which of the two failure modes you chose and why, because "at-least-once with an idempotent sink" is a design decision, not an accident.

ClickHouse schema
CREATE TABLE alerts (
  partition   Int32,
  seq         UInt64,
  rule_id     UUID,
  rule_title  LowCardinality(String),
  severity    Enum8('informational'=1,'low'=2,'medium'=3,'high'=4,'critical'=5),
  event_time  DateTime64(3),
  ingest_time DateTime64(3),
  host_id     LowCardinality(String),
  source      LowCardinality(String),
  fields      Map(String, String),

) ENGINE = ReplacingMergeTree
ORDER BY (partition, seq, rule_id)

05

Behavior under load

The deliverable of this phase is a written document, not a benchmark number. It answers three questions for each experiment below: where did the work queue, what fell behind first, and what happened to detection correctness while it was behind.

Required experiments
ExperimentWhat the document has to answer
Sustained 2x capacity, 30 minWhich stage saturates first, and what the lag curve looks like on recovery. Verify zero drop-ledger entries
Sustained 5x, 30 minWhether anything begins to fail rather than merely slow down. Broker disk, socket buffers, GC pressure
Consumer kill mid-batchWhether replay produces duplicate alerts and whether the sink collapses them. Verify the verdict digest is unchanged after recovery
Poison recordA record that panics the normalizer. It must land in the drop ledger and must not wedge the partition
Rule set reload under loadWhether verdicts straddle two RuleSetV values mid-batch. They must not; reload is atomic at a batch boundary
ClickHouse unavailable, 10 minWhere the backpressure surfaces, and whether alerts survive the outage
One partition offlineWhether the other partitions keep processing, and whether the canary alerts on the dead one
The interview answer

A missed detection and a delayed detection are different classes of failure. This phase exists so that you can say, with evidence, which one Signalman produces under overload and why that was the right trade for a detection system. That sentence is worth more than the throughput number.

Staleness and lag are separate on purpose. Lag counts records not yet consumed. Staleness is now() - max(event_time) among processed records, which catches an upstream that stopped producing. A pipeline with zero lag and rising staleness is broken, and only one of those two metrics can see it.

Alerting on absence

This is the piece the job description asks for by name, and it is about twenty lines of code.

A generator injects a synthetic event into events.raw on every partition every 30 seconds. The event is crafted to match one rule, signalman-canary, which exists only for this purpose and is loaded like any other rule. When the corresponding alert appears at the sink, signalman_canary_age_seconds resets. When it does not, the gauge climbs.

alerts/absence.yml
- alert: SignalmanCanaryStalled
  expr: signalman_canary_age_seconds > 120
  for: 2m
  labels:   { severity: page }
  annotations:
    summary: "No canary alert on partition {{ $labels.partition }} for 2m"
    runbook: "Pipeline is not producing detections. Check staleness, then
              the taxonomy version, then broker health. Assume detections
              are being missed until proven otherwise."

- alert: SignalmanRuleWentSilent
  expr: |
    increase(signalman_rule_matches_total[24h]) == 0
      and
    increase(signalman_rule_matches_total[30d]) > 0
  for: 1h
  labels:   { severity: ticket }
  annotations:
    summary: "Rule {{ $labels.rule_id }} matched in the last 30d but not today"

The canary catches a wedged consumer or a broken sink within two minutes. The silence detector catches the subtler failure: a taxonomy change renames a field, a rule stops matching anything, and nothing errors. It files a ticket rather than paging, because the base rate of legitimately quiet rules is high and a noisy absence alert would be self-defeating.

Noise budget

The severity split is the point. A SOC that gets paged for a rule going quiet will mute the channel within a week, and then the canary page gets muted with it. Absence alerting only works if the paging tier stays small enough to stay credible.

07

Compiled engine

v1 costs O(rules x predicates) per event. At 1,500 rules that is roughly 40,000 predicate evaluations per event, most of them on fields the event does not have. v2 compiles the whole rule set into one structure and evaluates the shared work once.

Predicate interning

Across the SigmaHQ corpus, the same leaf predicate appears in many rules. Image|endswith: '\powershell.exe' occurs in dozens. Compile every leaf into a canonical form, deduplicate into a table, and give each unique predicate an index. Evaluation fills a bitset of predicate results per event; the boolean trees then read from the bitset instead of touching the event.

internal/engine/v2/compile.go
type Program struct {
	Preds  []Pred            // deduped, indexed
	ByField map[string][]int // field name -> predicate indices
	Trees  []Tree            // one per rule, leaves are predicate indices
	Filter *ahocorasick.Matcher
	Always []int             // rules with no derivable required literal
}

Literal prefilter

For each rule, derive the set of string literals that must appear somewhere in the event for the rule to have any chance of matching. Build one Aho-Corasick automaton over all such literals and run the event's string fields through it once. Rules whose required literals are absent skip tree evaluation entirely.

The subtle part

A literal is only required if it sits in a conjunctive position with no negation above it. Harvesting literals from inside an OR, or from under a not, produces a prefilter that discards events the rule would have matched, which is a missed detection introduced by an optimization. Write the derivation as a separate function with its own property test: for every rule and every event in the corpus, assert that prefilterAdmits(rule, event) == false implies v1.Evaluate(rule, event) == false. Rules with no safe required literal go in Always, and the size of that set is a metric worth watching.

Field presence gating

Before anything else, intersect the event's field set with each rule's required field set. A process_creation rule against a network connection event exits on a bitset AND. This also preserves invariant 4: a gated-out rule still emits an explicit false verdict, it just does not walk the tree to produce it.

08

Equivalence

Four independent arguments, in increasing order of strength. Each one is cheap to run in CI once built.

Differential fuzzing against pySigma

pySigma is the reference implementation of the specification. Generate random but valid rules and random events, evaluate both under Signalman and under pySigma, and assert agreement. This tests the frontend against the specification, which nothing else in the project does.

test/fuzz/differential_test.go
func FuzzAgainstPySigma(f *testing.F) {
	// seed corpus: every rule in SigmaHQ that this engine accepts
	f.Fuzz(func(t *testing.T, ruleYAML, eventJSON []byte) {
		got, errG := signalman.EvalOnce(ruleYAML, eventJSON)
		want, errP := pysigma.EvalOnce(ruleYAML, eventJSON) // subprocess
		if (errG == nil) != (errP == nil) {
			t.Fatalf("acceptance mismatch: go=%v py=%v", errG, errP)
		}
		if errG == nil && got != want {
			t.Fatalf("verdict mismatch: go=%v py=%v", got, want)
		}
	})
}

Run the parser fuzzer separately, with no oracle, purely for panics and unbounded recursion on hostile condition strings.

Property tests

  • Determinism. Same corpus, rule set shuffled, digests identical. This is the property invariant 2 depends on.
  • Rule independence. Evaluating rules A and B together produces the same verdicts as evaluating each alone. Catches shared-state bugs in the interned predicate table.
  • Prefilter soundness. The implication stated in phase 07, run over the full corpus.
  • Idempotence. Re-ingesting an identical batch changes no alert row after merge.

Corpus replay

Replay the full historical event corpus through both engines offline and compare verdict digests per partition. This is the strongest offline claim available, because it is exhaustive over a fixed input rather than sampled. It runs in CI on every change to the frontend or either engine.

Shadow mode

v2 consumes events.norm alongside v1 and writes to verdicts.v2. It emits no alerts and has no consumers. The differ joins the two verdict streams on (partition, seq, rule_id) and classifies every disagreement.

Divergence classes and budgets
ClassBudgetHandling
v2 false negativezeroMissed detection. Halts the cutover immediately
v2 false positivezeroNoise the SOC would have to absorb. Also halts
Missing verdict, either enginezeroViolates invariant 1. Halts
Version skew during reloadtransientExcluded from the count when RuleSetV differs between the two rows. If this class is not empty at steady state, the reload is not atomic
Orderingn/aThe join is on Seq, so arrival order cannot produce a divergence
Keep the divergence log

Every disagreement found in shadow mode, with the rule, the event, the root cause, and the fix, goes in a running document. That document is the single best artifact this project produces, because it is direct evidence of the failure modes you found before users did. Expect the majority to come from the prefilter derivation and from null handling.

09

Cutover

Routing is per rule, by fnv(rule_id) % 100 < rolloutPercent. Rules move to v2 in a stable order, so advancing the percentage never moves a rule back, and a rule that has been serving from v2 keeps serving from v2. v1 continues to shadow every rule that v2 serves, for the entire rollout, which means the divergence detector is still armed on exactly the rules that are live.

  1. G0Offline equivalenceFull corpus replay digests match on every partition. Differential fuzzer clean for 1e8 executions. All property tests green.
  2. G1Shadow at full trafficv2 shadows 100% of rules for 7 days with 0 divergences in the three zero-budget classes. v2 p99 within target under production load.
  3. G21% of rules served by v2Hold 48 h. v1 still shadowing. Alert volume per rule unchanged within noise. Rollback is a config flag, measured to take effect in under 30 s.
  4. G310%, then 50%48 h at each step, same conditions. Any divergence at any step returns to the previous step, not to zero.
  5. G4100% served by v2v1 keeps shadowing and keeps consuming. No configuration change other than the flag. Rollback still exercised.
  6. G5Rollback game dayDeliberately roll back to v1 at full traffic, during business hours, and roll forward again. Measure both. A rollback path that has never been executed is a hypothesis.
  7. G6Retirement14 days at 100% with zero divergence, plus a successful game day. v1 is removed from the serving path and the shadow lane is torn down.
Decision / demote, do not delete

At G6, v1 leaves production but stays in the repository as the test oracle. The differential and replay tests keep running against it forever. The cost is one unused package. The benefit is that the codebase permanently contains two independent implementations of the semantics, and any future change to v2 has to convince both.

Write the retirement criteria before reaching G4, not after. Deciding what "safe enough" means while looking at a green dashboard is how systems get retired one week early.

Author surface

The users of a detection engine are not engineers. The product is a language, a CLI, and a feedback loop, and the loop has to close before merge rather than after deployment.

CLI

signalman test    rules/proc_dump.yml    # run fixtures
signalman explain rules/proc_dump.yml \  # show why an event matched
                  --event samples/lsass.json
signalman noise   rules/proc_dump.yml \  # FP load over the corpus
                  --corpus corpora/win-30d
signalman bench   rules/                 # per-rule eval cost

11

AI tooling policy

Use AI coding tools heavily on this project, and be able to say exactly where the trust boundary sits. In a detection system, a plausible-looking wrong answer is a security outcome, so the policy is about what counts as verification rather than about how much gets generated.

Generate freely

  • The differential fuzzer harness and the pySigma subprocess bridge.
  • Test fixtures and corpus generators. Volume matters more than elegance.
  • The ClickHouse SQL backend, which has an independent oracle in the in-process evaluator.
  • Metric wiring, dashboards, and alert rule scaffolding.
  • The parser itself, because it is the most heavily oracle-checked component in the project.

Write and review by hand

  • The drop path. It decides what is allowed to disappear.
  • Offset commit ordering. Getting it backwards produces silent loss that no test will catch by accident.
  • The prefilter literal derivation. Subtly wrong here means missed detections, and it looks correct.
  • The cutover flag evaluation and the rollback path.
The position

Generated code is unverified until an independent oracle disagrees with it and loses. On this project the oracles are pySigma for the specification, v1 for the semantics, and corpus replay for the whole. The productive use of AI tools here was not writing the parser faster; it was that having a cheap way to generate ten thousand rule and event pairs made differential testing affordable, and the differential testing is what made the parser trustworthy.

The three documents

These are the deliverables that a hiring panel will actually read. Write them as you go, because reconstructing them at the end produces a worse and less honest version.

  1. Behavior under load. Where it queues, what falls behind, what happens to correctness when it does.
  2. Equivalence and cutover. The four arguments, the gate ladder, the divergence log, and the retirement criteria with their dates.
  3. Detection author guide. The supported subset of Sigma, what is rejected and why, how to read a noise report, and what the budgets mean.
