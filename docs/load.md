# Behavior under load

What Signalman does when it is offered more than it can handle, or when a
part of it breaks while traffic is flowing. Spec phase 05 asks three
questions of each of seven experiments: where did the work queue, what fell
behind first, and what happened to detection correctness while it was
behind. This document answers them with what has actually been run.

**Every result here is in-process, in-memory broker.** `pipe.Pipeline` ran
over `broker.Memory` on one Apple M1 Pro (8 cores, 16 GB, Go 1.27.1), with
the load generator, the pipeline, and the output checker sharing the same
cores. No Redpanda, no ClickHouse, no network. Each section ends with what
still needs a real Redpanda or ClickHouse run. Nothing below was measured
against either, and where a question can only be answered there, it says
"not run".

## The short answer

Under every overload and failure that was run, Signalman produced delayed
detections and no missed ones. Across 2.0 million generated events, every
`events.raw` offset ended as exactly one verdict record (one verdict per
rule) or one drop ledger entry. The only drops were the records built to
be dropped. The per-partition verdict digest, after collapsing redelivered
copies, equaled a clean single-threaded replay of the same log through v1
in every experiment where the comparison means something. The price was
latency. At 2x, an event waited up to 94 s before its verdict was durable,
because the backlog sat in the broker as consumer lag and the in-process
queues stayed at their bounds.

That is the trade the design makes on purpose. A delayed detection can be
reported on afterwards; a missed one cannot.

## How it was run

```bash
SIGNALMAN_LOAD=1 SIGNALMAN_CORPUS=/path/to/sigmahq SIGNALMAN_LOAD_BASELINE=2465 \
  SIGNALMAN_LOAD_OUT=out go test -run TestLoadExperiment -v -timeout 2h ./internal/loadtest/
```

- Rule set: the 1,236 accepted rules of the SigmaHQ `rules` tree, engine v1.
- Corpus: 24,720 events generated by `loadtest.FromRules` (20 per rule,
  seed 1), aimed at the rules so that most events match something, and
  cycled. Generated records the normalizer would drop are left out, so a
  drop during a run can only come from the pipeline or from an injected
  bad record.
- Pipeline: `signalmand`'s defaults. 8 partitions, max poll 500 (the batch
  size), 8 normalize and 8 match workers, stage queues of 1024, 4 in-flight
  batches.
- 1x is 2,465 events/s, the capacity measured from a cold backlog
  (`docs/results.md`). Sustained runs committed faster than that once warm:
  2,912/s under 2x and 3,178/s under 5x. So "2x" was about 1.7 times the
  warm rate and "0.8x" (1,972/s) about 0.65 of it. The multiples below are
  of the cold figure.
- The tap (`internal/loadtest/tap.go`) takes the output topics in place of
  the broker. It accepts each batch's outputs as durable, then checks them:
  one verdict per rule of the batch's RuleSetV, one RuleSetV per batch,
  alerts equal to matched verdicts, and at the end exactly one outcome per
  offset. Its queue was empty at every sample in the recorded run (peak 0).
  That is sampled, so a queue that filled and emptied between samples
  would not show; the tap now counts every call that had to wait for it
  (`tap_blocked_sends` in each report).
- "Digest equals replay" means the run's verdicts, one copy per event,
  fold to the same per-partition digest as reading `events.raw` back and
  evaluating each record once with v1 outside the pipeline.
- Latency is from the `events.raw` produce to the moment the event's outputs
  were accepted, so it includes time spent as broker lag.
- Durations are scaled down from the spec's (30 minutes, 10 minutes)
  because the in-memory broker keeps every record. The long runs belong on
  Redpanda.

Per-run JSON reports (samples, lag curves, stage saturation order) are
written to `SIGNALMAN_LOAD_OUT`; the figures below come from the run of
2026-10-21.

### Where the bounds are

Ingest polls a batch, queues it on the in-flight batch queue (4), and
feeds its items to normalize (queue 1024), then match (1024), then the
sink (1024). The sink writes batches in poll order and commits each one
after its outputs are durable. When any stage stops keeping up, the queues
in front of it fill, ingest blocks on the full batch queue, and the
consumer stops polling. The backlog then lives in `events.raw` as
consumer lag, not in the process. The number of admitted, uncommitted
records is bounded by `(inflight + 2) x max-poll` = 3,000.

## Sustained 2x capacity

2x of 2,465 = 4,930 events/s for 120 s (the spec says 30 minutes), then
no input until drained. 591,600 events sent.

**Where work queued.** In the broker. Lag grew linearly at about 2,000
records/s, to 246,500 at the end of the load. In-process queues sat at
their bounds the whole time: in-flight batches 4 of 4, sink 1024, match
1024. Normalize peaked at 492 and never filled.

**What fell behind first.** The in-flight batch queue filled at 0.2 s, then
the sink queue at 0.7 s, then the match queue at 1.5 s. A full sink queue
means the single sink goroutine, which builds and writes every output
record (a 1,236-verdict record per event), was not draining the match
workers' output. With v1 at this rule set, the match pool and the sink run
at their limit together; normalize has headroom.

**Recovery.** Committed throughput during the load was 2,912/s. After the
load stopped, lag fell from 246,500 to 0 in 93.9 s, a slope of about
2,600/s, steady with no stall. Latency during the load: p50 27.9 s, p99
49.6 s; worst over the whole run 94.5 s, the last record of the backlog.

**Correctness.** Zero drop ledger entries (the acceptance target). 591,600
of 591,600 events evaluated, none missing, none with both outcomes. 546,964
matches. Digest equals replay on all 8 partitions. Peak heap 981 MB,
which includes the in-memory broker's copy of every raw record; 1,632 GCs
with 409 ms of total pause.

**Still needs Redpanda.** The 30-minute duration; broker fetch and disk
behavior with a quarter-million-record lag; the lag and staleness metrics as
Prometheus would scrape them. `signalman-sink` reads the `alerts` topic as
a separate process and is not in the harness, so alert inserts were not
part of the sink's cost.

**Run on Redpanda since** (2026-11-08, `deploy/docker-compose.yml` on an
8-core laptop, `signalmand -rules rules`, both `signalman-sink` lanes, 21
rules). `loadgen -rules rules -measure-baseline 40000 -profile
2:30m,0:10m` measured 1x in process at 66,954 events/s and offered
133,908/s. The producer and Redpanda on this machine took 21,134/s, so the
30-minute schedule ran 85 minutes behind and was stopped there after
108,262,400 records with 0 retries. signalmand evaluated about 18,000/s
throughout, and the gap queued in Redpanda. Lag on `events.raw` rose to
15.05 million records, then fell to 0 in 15 minutes once the producer
stopped. Over the whole run, drop ledger entries stayed at the 355 already
in the topic (zero new), `signalman_audit_violations_total` stayed 0, and
no process logged ERROR. The alerts lane ended with no lag and 0 dead
letters. ClickHouse holds 112,287,486 events with no repeated `(partition,
seq)` on any partition. `signalman hunt` over all of partition 4
(3,475,778 events) returned exactly the 2,139,080 `(rule, partition, seq)`
alerts stored for it, none on one side only. A full hunt was not run,
because 57.6 million hits do not fit this machine, and an exact-distinct
count over the whole table got ClickHouse OOM-killed in the 7.75 GB compose
VM. That restart was an unplanned ClickHouse outage of about a minute. Both
sinks logged `insert failed, retrying the batch; not polling until it
lands`, then resumed with no dead letters. This does not answer 2x of the
pipeline's own capacity on Redpanda, since the producer, not signalmand,
was the limit.

## Sustained 5x capacity

5x = 12,325 events/s for 60 s (spec: 30 minutes), then drain. 739,500 sent.

**Where work queued.** In the broker. Lag reached 549,800 at the end of
the load, growing at about 9,200/s. In-process queues were at their bounds
from the first second, exactly as at 2x: the bound does not move with the
offered rate.

**What fell behind first.** In-flight batches at 0.1 s, match at 0.5 s,
sink at 0.6 s. Normalize peaked at 492.

**Whether anything failed rather than slowed.** Nothing failed in process.
Committed throughput during the load was 3,178/s, slightly above the 2x
run, so overload did not degrade the pipeline's own rate. The backlog
drained in 178.5 s. The generator never fell more than 75 ms behind its
schedule, because the in-memory broker accepts writes without limit. Peak
heap 1,014 MB, mostly the broker's copy of 740k raw records; 1,780 GCs,
362 ms total pause. No goroutine, queue, or buffer grew with the offered
rate. Latency during the load: p50 24.1 s, p99 44.2 s; worst 178.6 s.

**Correctness.** Zero drops, all 739,500 events evaluated, digest equals
replay.

**Still needs Redpanda.** The questions the spec actually asks here are
broker disk, socket buffers, and producer backpressure: what happens when
the broker cannot keep accepting 12k events/s for 30 minutes. The
in-memory broker cannot answer any of them. Not run.

## Consumer kill mid-batch

0.8x (1,972/s) for 60 s. Five times, 10 s apart, the consumer was killed
at the worst moment for duplicates: right after a batch's outputs were
accepted as durable and before its offsets were committed. Each kill was
followed by 2 s down and a restart of a fresh `pipe.Pipeline` on the same
group. 118,320 sent.

**Where work queued.** In the broker while the consumer was down: lag
peaked at 5,200, just after the first restart. Each restart re-read
everything after the last commit, so the batches in flight at the kill
were evaluated twice.

**What fell behind first.** After a restart, the in-flight batch queue,
then normalize and match (12.2 s), then the sink (12.7 s), all while the
restarted consumer caught up. Lag fell back between kills (100 at 30 s)
and drained 1 s after the last restart.

**Duplicates and the sink.** The replay produced duplicates, as
at-least-once delivery promises: 500 duplicate verdict records and 467
duplicate alerts. The recorded run compared each redelivered verdict
record with its first write by rule set and matched rules, and none
differed; since then the tap compares the record bytes (see "Since the
recorded run"). 110,098 alert records collapse on
`(partition, seq, rule_id)` to 109,631 distinct alerts. That is exactly the
109,631 matches the partition offline run, which replayed the same 118,320
events with no kill, produced.

**Correctness.** Digest after recovery equals replay on every partition
(the acceptance target). No event missing, no drop.

**Still needs Redpanda and ClickHouse.** A kill here cancels a goroutine
tree; a real `kill -9` of `signalmand` also loses the producer's buffered
records and needs the group to notice a dead member (session timeout,
rebalance). That the alert table's ReplacingMergeTree collapses the
duplicates was checked by counting distinct keys, not by ClickHouse;
`signalman-sink` was not part of the run.

**Run on Redpanda since.** One `kill -9` of `signalmand` at 1,000 events/s,
with both sink lanes running, then a restart on the same group: the audit
stayed at zero violations, and `signalman hunt` over the stored events
equaled the stored alerts row for row (`docs/results.md`). That is one
kill at an arbitrary moment, not five at the worst one.

**Five kills on Redpanda** (2026-11-09). `loadgen -rules rules -baseline
10000 -duration 6m` sent 3,600,000 records with 0 retries while
`signalmand` was `kill -9`ed five times, 60 s apart, and restarted a
second later on the same group. At 10,000 events/s with 500-record polls
every kill lands with batches in flight. Prometheus over the window shows
0 drop ledger entries and 0 audit violations across 148 closed audit
windows. Lag returned to 0 two minutes after the load ended. ClickHouse
stores the run's 3,600,112 events (the load plus canaries) once each, with
no repeated `(partition, seq)` even before merges, so the redelivered
batches did not reach the table twice. `signalman hunt` over all of
partition 4 returned exactly the 2,207,683 alerts stored for it. The kill
moment was a timer rather than a chosen worst point such as mid-commit;
the poll-to-commit window is most of each cycle at this rate.

## Poison record

0.8x for 60 s. One record in every 500 was bad, all on one host (and so
one partition, 5), cycling through a record that makes the normalizer
panic (`Normalizer.SetFault`) and one record for each of the seven decode
failures. 118,320 sent, 234 of them bad.

**Where work queued.** Nowhere special. Lag rose to 6,100 at 20 s and fell
back to about 500 by 50 s, the same as in other 0.8x runs. The cause of
that early rise was not isolated.

**What fell behind first.** In-flight batches, then sink, then match;
normalize never filled. The bad records did not change the order.

**Correctness.** Every bad record became exactly one drop ledger entry with
its reason: 33 `panic`, and 28 or 29 each of `parse`, `invalid-utf8`,
`value-too-long`, `nested-value`, `duplicate-field`, `missing-source`, and
`event-time`. That equals, reason by reason, the bad records the generator
sent. No good record was dropped, and the digest equals replay. The
partition did not wedge: latency on partition 5 (p50 1.49 s, p99 3.61 s)
was no worse than on the other seven (p50 1.52 s, p99 3.97 s).

This run predates the `unknown-source` drop reason. The experiment now
also injects an `unknown-source` record, and generated records carry the
source `sysmon`, since the normalizer drops any source not in
`pipe.Sources`.

**Still needs Redpanda.** Little: the drop path is the same code against
either broker. A poison record from a real source, rather than one injected
through a fault hook, has not been seen.

**Run on Redpanda since** (2026-11-09). During a 3-minute load at 2,000
events/s, `rpk topic produce events.raw` wrote 200 malformed records with
no source header. The `drops` topic holds exactly 200 new entries, all
`missing-source`, each with its partition, offset, seq and the raw bytes.
The 360,000 good records are stored once each, and the audit stayed at 0
violations. The source check runs before JSON parsing, so these never
reached the `parse` reason.

## Rule set reload under load

0.8x for 60 s, with the slot reloaded every 250 ms, alternating between
the full 1,236-rule set and a set 10% smaller under a different RuleSetV.
236 reloads. 118,320 sent.

**Where work queued and what fell behind.** As in the other 0.8x runs:
in-flight batches, then sink and match; normalize peaked at 288. Lag
peaked at 3,000. Reloads did not move it.

**Whether verdicts straddled two RuleSetV values.** No. Of 1,116 batches,
none held verdicts under two versions; each verdict record had exactly the
verdicts its own version owes. 57,920 events were evaluated under the full
set and 60,400 under the smaller one. A batch reads the slot once, when
ingest forms it, so a reload lands between batches by construction.

**Correctness.** Invariant 1 holds: every event has its verdicts, none
missing, no drop. There is no replay digest here, because the run is
deliberately a mix of two rule sets.

**Still needs Redpanda.** The reload trigger in production is `SIGHUP` to
`signalmand`, which loads the rule directory from disk; this run called
`Slot.Store` directly, so loading time and a failed reload under load
were not exercised. The batch boundary does not depend on the broker.

**Run on Redpanda since** (2026-11-09). Three `SIGHUP`s to one
`signalmand`, 45 s apart, during a 3-minute load at 2,000 events/s. Each
logged `rule set reloaded; applies from the next batch` with the same
`ruleset_v`, the process stayed up, no drop or audit violation appeared,
and every event was stored once. The Plan C soak also reloaded three times
mid-run (`docs/results.md`). A failed reload under load, from a rule
directory that no longer loads, was not tried.

## ClickHouse unavailable

**The ClickHouse experiment itself: not run.** `signalman-sink` was not
part of the run, and there is no ClickHouse here. What ran instead is
its in-process analogue: every output write the pipeline's sink makes
failed for 30 s (from 20 s to 50 s of a 90 s run at 0.8x, spec: 10 minutes).
From the pipeline's side that is the same event: its sink cannot make a
batch durable. 177,480 sent.

**Where the backpressure surfaced.** At the sink first, then everywhere
upstream within about two seconds. During the outage, nothing was
committed on any partition, and ingest admitted no new records after the
first 2 s. What the process held was bounded: the 4 in-flight batches, 400
items in the sink queue, 64 in match, none in normalize. Everything else
waited in the broker; lag climbed at the offered rate to 62,900.

**What fell behind first.** The in-flight batch queue (19.8 s, as the
outage began), then match and sink when the outage ended and the backlog
came in.

**Whether alerts survived.** Yes. The sink retried the same batch with
backoff doubling to 5 s (11 refused attempts in 30 s) and never dropped
it. Afterwards all 177,480 events had their verdicts, 164,051 alerts, zero
drops, and the digest equals replay. Lag was back to its pre-outage level
55.4 s after the outage ended. The pipeline only had about 1,000 events/s
of headroom over the offered rate to work the 60k backlog off with. The
backoff cap means the first successful write after an outage can come up
to 5 s late.

**Still needs ClickHouse and Redpanda.** The real experiment: the alert
sink inserting into ClickHouse, ClickHouse down for 10 minutes, and
whether the sink's own retry and the `alerts` topic retention hold up for
that long. Not run.

**Run on Redpanda since** (2026-11-09). `loadgen -rules rules -baseline
2000 -duration 15m` sent 1,800,000 records with 0 retries, and
`docker compose stop clickhouse` held ClickHouse down from 00:13:51 to
00:23:52 UTC. Both sink lanes logged `insert failed, retrying the batch;
not polling until it lands` and held their batch, so the backlog stayed in
the `alerts` and `events.norm` topics. signalmand never noticed, because
its output is the topics. After the restart both lanes caught up in about
3 minutes with 0 dead letters and no ERROR. ClickHouse stores the
1,800,264 events (load plus canaries) once each, and `signalman hunt` over
all of partition 4 returned exactly the 2,242,003 alerts stored for it.
`SignalmanSinkCanaryStalled` fired: the sink canary age climbed to 610 s.
The sinks' `signalman_consumer_lag_records` did not. A sink that stops
polling stops refreshing that gauge, so it sat at the last value (1,043
and 2,100) for the whole outage while the real backlog grew to about 1.2
million records. The canary, not lag, is what pages for a stalled sink.
Fixed since: each retry now asks the broker for the topic's log end
(`refreshLag` in `internal/pipe/chsink`, `TestSinkLagGrowsDuringOutage`).
In a 2-minute outage under 2,000 events/s after the fix, the events lane's
lag read 55,708, 115,816, 175,924 and 236,032 at 30 s steps, then fell to 0
after ClickHouse returned, with 0 dead letters.

## One partition offline

0.8x for 60 s. From 15 s to 45 s, partition 3 of `events.raw` could not be
fetched: the harness held back its records from the consumer and released
them in order when it came back, which is what a partition with no leader
looks like to a consumer. 118,320 sent.

**Whether the other partitions kept processing.** Yes. During the outage
each of the other seven partitions committed 6,900 records and partition
3 committed none. Latency on the live partitions stayed normal: p50 40 ms,
p99 203 ms. The batches simply had no records from partition 3.

**Where work queued and what fell behind.** Partition 3's records waited
(lag grew to 6,212 by 40 s, about one eighth of the offered rate times the
outage). When it came back, its held records arrived as a burst: normalize,
match, and sink filled at 45.1 to 45.5 s, and the backlog was gone before
the load ended at 60 s. The records that waited out the outage carried the
run's worst latencies (p99 26.5 s, max 30.5 s), which is the outage length.

**Correctness.** Nothing lost, nothing duplicated: all 118,320 evaluated,
digest equals replay.

**Whether the canary alerts on the dead partition.** Not run. The canary
and silence detector (Plan E) were not part of the harness. From the
partition's commit and lag, this run shows what the canary has to see: a
partition whose committed offset stops moving while its lag grows.

**Still needs Redpanda.** A real leader loss also affects producers: a
generator or source writing to that partition blocks or errors, which this
simulation does not model. A rebalance and the consumer's fetch error
handling are also untested. Not run.

## Since the recorded run

The figures above come from the run of 2026-10-21, on the load harness
branch before the review fixes of the pipeline, sink, observability,
shadow and cutover work (stack layers 3 to 9) were merged into it: the
output record size cap and its two drop reasons (`record-too-large`,
`output-too-large`), permanent produce errors, `StartOffsets` for the
audit floor, the rebalance commit fix, and the rest. The seven experiments
were not re-run in full afterwards. After the merge, sustained 2x (scale
0.05, 29,580 events) and sustained 5x and partition offline (scale 0.1)
ran on the 1,236 SigmaHQ rules: no drops, no missing offsets, no
duplicates, digest equal to replay.

Assertions added after the recorded run, which the recorded numbers were
not checked against:

- `Correctness.OK` fails on any redelivered verdict record whose bytes
  differ from its first write (`redelivery_changed`); before, a
  redelivery was compared on rule set and matched rule indices, and the
  count was reported but not asserted. The reload experiment uses
  `OKAcrossReloads`, where a redelivery under the other rule set is
  allowed.
- Sustained 5x asserts that its digest equals the replay. The recorded
  run reported it (equal) but did not fail on it.
- Partition offline asserts no duplicate verdict records, alerts or drops.
- The tap counts output calls that waited for its checking pool
  (`tap_blocked_sends`), where the recorded run sampled the queue depth.
- `Replay` stops on a permanent produce error and counts records resent
  after a failed call (`Resent`): a Kafka produce can write part of a call
  before it fails, so up to that many records may be duplicates in
  `events.raw`. In process, the broker writes all of a call or none.

## Running it

```bash
# the baseline (capacity and latency at 0.5x and 0.8x)
SIGNALMAN_LOAD=1 go test -run TestLoadBaseline -v -timeout 1h ./internal/loadtest/
# all seven, or one by name
SIGNALMAN_LOAD=1 go test -run 'TestLoadExperiment/consumer-kill' -v -timeout 2h ./internal/loadtest/
```

| Variable | Effect |
|---|---|
| `SIGNALMAN_LOAD` | required; the load runs skip without it, so `make check` stays fast |
| `SIGNALMAN_CORPUS` | SigmaHQ clone (default `corpora/sigmahq`); without it the 21 rules in `rules/` are used |
| `SIGNALMAN_LOAD_BASELINE` | use this rate as 1x instead of measuring it |
| `SIGNALMAN_LOAD_SCALE` | multiply every phase duration |
| `SIGNALMAN_LOAD_PER_RULE` | generated events per rule (default 20) |
| `SIGNALMAN_LOAD_OUT` | directory for the JSON reports |

Against Redpanda, `cmd/loadgen` does the producing side:
`loadgen -rules <dir> -measure-baseline 40000 -profile 2:30m,0:10m` measures
1x in process, then replays at 2x for 30 minutes into `events.raw` on
`-brokers`. `signalmand` consumes it, and its metrics show the rest.
